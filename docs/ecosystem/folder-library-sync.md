# Manual folder sync

In the local app, open the folder library. Drop images into the library's
`public/images/Inbox`, or organize them in any folders beneath `public/images`.
Choose **Scan folders** to review changes, then **Apply sync** to save them.
Scanning alone writes nothing. The configured library root is still
`library-exports/moodboard-library-2026-09-21` by default, or
`MOODBOARD_LIBRARY_ROOT` in the local server environment.

The scan recursively checks `public/images`, `public/image-thumbs`, and
`public/image-thumbs-mobile`. It hashes files during this explicit operation;
ordinary catalogue reads still use inexpensive filesystem checks. Hidden image files and folders are scanned; hidden non-image files are ignored. Symlinks are not followed by the scanner. New JPEG, PNG,
WebP, AVIF and GIF images are supported; other formats and unreadable images are
reported for review. New images are decoded during review; the decoder has a
100-megapixel input limit. Animated images use their first frame for thumbnails.

## What applying does

- New images receive a stable UUID and legacy-compatible ID. Their initial name
  comes from the filename, and their folder comes from their actual location.
  Tags start empty; folders never determine tags.
- New desktop/mobile WebP thumbnails are created at maximum edges of 1,200/560
  pixels, preserving aspect ratio and orientation without enlarging small images.
  They live under the corresponding thumbnail folder, named with the stable UUID.
- Missing registered originals or thumbnails are relinked only when an unregistered
  file has the same SHA-256 fingerprint and the match is unambiguous. When the filename retains a stable UUID, that UUID plus a matching fingerprint
  resolves otherwise identical duplicates. Names without IDs alone never establish identity. Moving an original updates its displayed folder.
- Existing IDs, complete source metadata, metadata edits, presentation settings,
  and board placement references are retained. Deleted originals are listed as
  removals in the review and disappear from the library after Apply.

The app does not move or rename originals. Existing thumbnails can remain in their
registered locations when only originals move; moved thumbnails are detected
independently. Sync refreshes both thumbnails for edited main images; standalone thumbnail changes remain review issues.
Ambiguous duplicate content, missing fingerprints, and unsupported/unreadable
files are reported and skipped. Edited main images are handled as described below. They do
not block unrelated verified additions and moves. There is no automatic duplicate
merging or missing-original recovery.

## Persistence and failure handling

The original `manifest.json` and `metadata/items.ndjson` stay intact. Sync writes a
complete version-1 `metadata/catalogue.json` containing `{ version, baseRevision,
items }`. `baseRevision` fingerprints the original manifest and item-file bytes;
manual modification of that baseline is rejected. The reader validates the active
catalogue, retains all baseline identities (including removed records for recovery), resolves active assets, and derives current
inventory/folder counts. `baseManifest` remains available in the Node snapshot.
The existing `metadata/edits.json` overlay applies to both old and new UUIDs.

A single catalogue file avoids committing the item list and its count separately.
Apply takes the same `metadata/edits.lock` as metadata saves, rescans and checks the
review revision, generates thumbnails, and saves the previous catalogue into
`metadata/sync-backups`. It flushes the new catalogue and atomically renames it into
place. Changes between scan and apply require a fresh review. Backup failures
prevent catalogue replacement. Ordinary failed applies remove only thumbnails
created by that attempt; originals and previously registered thumbnails stay intact.

A crash can leave an `edits.lock`, `.catalogue-*.tmp`, or unregistered thumbnails.
Stop all local app servers before inspecting/removing a stale lock. Temporary
catalogues are never loaded automatically; orphan thumbnails are not automatically
registered or deleted. Do not remove files from a still-running sync.

Back up the whole metadata directory alongside the images and thumbnails. An old
catalogue backup may predate images referenced by newer metadata edits; restoring
requires a matching metadata set. There is no restore or backup-pruning UI yet.
The initial catalogue backup contains the original records. Saving the synced
catalogue does not rewrite `appState.json` or `edits.json`.

## Local API and boundaries

`POST /__folder-library/sync/scan` returns a client-safe review with relative paths,
counts, issues and a revision. `POST /__folder-library/sync/apply` accepts that
revision only after a review was generated by this server. Both require a local,
same-origin JSON request. The server exposes neither raw metadata nor arbitrary
filesystem write paths. Reloading the catalogue after apply shows new and moved
items. Browser IndexedDB and local storage remain untouched.

Boards are still read-only. Cloud access, cloud conflict resolution, folder moves
inside the app, standalone thumbnail repair and visual redesign are outside
this change. The local server is required; a static Vercel deployment cannot scan
local folders.

Tests cover additions, thumbnail dimensions, Unicode paths, repeat scans,
original/thumbnail moves, metadata and board preservation, duplicates, missing and
changed files, stale previews, symlinks, write locks, backup rollback, catalogue
validation, and the same-origin API. The real export was scanned without applying:
1,922 records, zero new images, zero moves, and no scan issues. Its pre-existing
26 fallback originals and one metadata-only record remain as before.

Final validation: 590 tests and the production build pass. A temporary-library
browser check verified preview/apply, loaded thumbnails, renamed-image metadata,
board links, editing new records, reopening, no-op scans, stale-preview rejection,
and mobile layout. No browser storage was accessed. The real library was only
read; no sync was applied to it during testing.


## Deletions and duplicate moves

A missing registered main image under `public/images` is now proposed for removal
when the scan finds no unresolved move candidate. This applies to originals and
registered preview fallbacks. Metadata-only records, missing thumbnails, changed
files, and ambiguous moves are not interpreted as deletions. An unavailable
`public/images` root aborts the scan; skipped symbolic links prevent inferred
removals. Apply always rechecks the review revision.

A filename ending in `--<itemUuid>` (or exactly `<itemUuid>` before its extension)
identifies a moved record only when its stored SHA-256 also matches. UUID matches
are resolved before content-only matches, so identical copies cannot steal one
another's identity. A unique filename retaining an ID with changed bytes is reviewed as an edited image, as described below.

Removed records receive `syncDeletedAt` in the atomic catalogue. They are excluded
from the browser catalogue, media routes, active counts, and search, while their
complete records, metadata edits and existing thumbnails remain recoverable.
Board placements remain as missing-image placeholders; they are not rewritten.
Restoring the same file at its registered path, or moving it with its UUID intact,
restores the same record and its metadata on the next applied sync.

Validation includes the reported duplicate case: the real library scan proposes
one UUID-verified move for IMG_9189 into Vintage/EU/France and one removal for
IMG_9189 2, without ambiguous matches. This real-library preview was not applied
by the implementation tests.


## Cropped or otherwise edited images

Scan lists **edited images** separately. A main image saved over its registered
path can be updated in place. A moved and edited image is matched by a unique
stable UUID retained in the filename. Multiple files claiming the same UUID stay
unresolved. A moved image with changed contents and no preserved UUID cannot be
reliably matched and is not automatically merged with a record.

Edited candidates are decoded during scan. Apply revalidates the review, reads
one verified source buffer, and generates both thumbnail sizes from those same
bytes. The catalogue receives the new path, folder, dimensions, size and SHA-256;
IDs, metadata edits, tags, source provenance, image kind, presentation settings and
board placements stay intact. Edited preview fallbacks remain marked as fallbacks.

Refreshed thumbnails get new versioned filenames rather than overwriting old
ones. Only after both are written does the atomic catalogue switch point to them.
A failed commit removes newly generated files and leaves the previous catalogue
and thumbnail files intact. Old thumbnail versions remain available for catalogue
backup recovery; pruning is not part of sync yet. Ordinary reads do not decode
images or regenerate thumbnails.

Validation includes saved-in-place crops, moved crops with stable IDs, repeat
scans, preserved metadata/boards, thumbnail dimensions, corrupt edits, conflicting
UUID copies, and rollback after backup failure. A read-only scan of the real
library now lists images-1125, images-479 and images-847 as three edited images in
People/Celebrities with no unresolved matches. No real-library apply was performed
by the implementation tests.
